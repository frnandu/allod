## Which test-network LSPS2 LSPs exist (Mutinynet, signet, testnet4, testnet3)?

### Takeaway
The best-documented LSPS2 LSP on a test network is Megalith's Mutinynet node, `03e30fda71887a916ef5548a4d02b06fe04aaa1a8de9e24134ce7f139cf79d7579@64.23.192.68:9736`. It asks for no token, and Alby Hub, OpenBazaar and others use it as their LSPS2 default for Mutinynet. It was live on 2026-11-25. There are other Mutinynet options: a second Megalith node aliased "Megalith LSPS2 MutinyNet" (`02d71bd1…@143.198.63.18:9735`), "See"/"lsps mutinynet" (`0371d6fd…@3.84.56.108:39735`, token `4GH1W3YW`) and Olympus Mutinynet, which is LSPS1. I found no public LSPS2 LSP on testnet4 or on plain signet. On testnet3, only Olympus (LSPS1) is clearly identified.

### Inferences
- For testing ldk-server LSPS2 on Mutinynet, `03e30fda71887a916ef5548a4d02b06fe04aaa1a8de9e24134ce7f139cf79d7579@64.23.192.68:9736` with any or no token is the default to try first. Alby treats it as LSPS2 in production config, and OpenBazaar got JIT invoices from it in a live test. `02d71bd1…@143.198.63.18:9735` (aliased "LSPS2") is a plausible fallback.
- Megalith's nodes do not set bit 729 even though they serve LSPS2, so bit 729 cannot be used as a filter: missing bit 729 does not mean LSPS is unsupported.
- No public testnet4 LSPS2 LSP was found, which matches OpenBazaar's statement. Allod's testnet4 deployments would need no-LSP mode or a self-hosted LSP.
- Olympus on Mutinynet and testnet3 advertises bit 729 and serves LSPS1 (ZEUS config). I found no source saying it serves LSPS2.

## Mainnet LSP-looking nodes: aliases, sockets, size, liveness; feature bits for LSPS0

### Takeaway
Explorers show the LSPS0 feature bit: mempool.space's node API returns `features` with bit numbers, and bit 729 is `option_supports_lsps` (bLIP-50). On mainnet, these nodes advertise 729: "Olympus by ZEUS", "LSPS1-BOS get-inbound-channel", "LQwD-Lspd-ldk" and "breez.diem.lsp". Megalith's LSPS2 node does not. The large mainnet LSP-branded nodes are Megalith LSP, Olympus, Flashsats, LQWD, Blocktank, Amboss/Magma and LNServer. Most of these sell LSPS1 or their own protocols, not LSPS2.

### Cited Findings
- bLIP-50 (LSPS0) says: "LSPs MAY set the `features` bit numbered 729 (`option_supports_lsps`) in both the `init` message… and in their own advertised `node_announcement`". It also says the bit may be set "if it supports at least LSPS0… even if it does not support some of the LSPS specifications", and clients MUST NOT set it. The bLIPs README lists bLIP-50 LSPS0, bLIP-51 LSPS1, bLIP-52 LSPS2 and bLIP-55 LSPS5 as Active — [bLIP-0050](https://github.com/lightning/blips/blob/master/blip-0050.md); [bLIPs README](https://github.com/lightning/blips/blob/master/README.md)
- mempool.space returns `features: [{bit, name, is_required, is_known}]` per node; bit 729 shows as `unknown` by name but appears by number — [mempool.space node API](https://mempool.space/api/v1/lightning/nodes/034066e29e402d9cf55af1ae1026cc5adf92eed1e0e421785442f53717ad1453b0). Amboss's public GraphQL has a `features` type (its field is `feature_id`, not `bit`). 1ml's JSON has no features field — [api.amboss.space/graphql](https://api.amboss.space/graphql), [1ml JSON](https://1ml.com/node/034066e29e402d9cf55af1ae1026cc5adf92eed1e0e421785442f53717ad1453b0/json)
