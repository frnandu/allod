# Validation/CPU side of post-snapshot sync (Bitcoin Core v31.1, snapshot 935,000 → tip ~974,500)

Local observations (read-only, 2026-11-04 ~09:20 UTC). Host: Intel Core Ultra 7 155H, `nproc` = 22, `/proc/cpuinfo` flags include `sha_ni avx2 avx_vnni bmi2 sse4_1` (no AVX-512).
- `debug.log` of `allod2-bitcoind-1`: `Bitcoin Core version v31.1.0 (release build)`, `Using the 'x86_shani(1way;2way)' SHA256 implementation`, `Script verification uses 15 additional threads`, `Assuming ancestors of block 00000000000000000000ccebd6d74d9194d8dcdc1d177c478e094bfad51ba5ac have valid signatures.`, signature cache and script execution cache each 16 MiB (524,288 entries), dbcache 2048 → `2038.0 MiB for in-memory UTXO set`.
- **The running config is not the one in the brief.** `/data/bitcoin.conf` (generated by `bitcoind-entrypoint.sh`, "Initial sync profile ... replaced after the sync (sync-tuning.sh)") has `blockfilterindex=0`, `txindex=0`, `prune=10000`, `blocksonly=1`, `dbcache=2048`. The log confirms `Config file arg: blockfilterindex="0"`. So the filter index is already off during this sync.
- Container memory limit is **6 GiB**, not 30 GB (`docker stats`: 3.8 GiB / 6 GiB used during the snapshot load). That limits how far dbcache can be raised.
- Timeline: the node started at 08:43, ran a normal IBD from genesis to height 269,636 (it reached ~269k by 08:59 because those blocks are below assumevalid and small), then paused the network (`.fastsync-network-paused`) and ran `loadtxoutset` at 09:08 on a 9.39 GB `utxo-snapshot.dat` for the 935,000 snapshot (`0000000000000000000147034958af1652b2b91bba607beacc5e72a56f0fb5ee`). Loading 164,241,311 coins took 09:08:27 → 09:19:08 (~10.7 min, with intermediate flushes of ~21.6 s at 2.1 GB of cache). At 09:21 one `b-http` thread was at ~91% CPU, which is the snapshot-hash/activation step. `getchainstates` still showed only the 269,636 chainstate. So no post-snapshot block-validation rate could be measured yet.

## 1. Default assumevalid in v31.1, and how many of blocks 935,000→974,500 get script checks

### Takeaway
The v31.1 mainnet default assumevalid is block **938,343** (`00000000000000000000ccebd6d74d9194d8dcdc1d177c478e094bfad51ba5ac`). After the snapshot, only 3,343 blocks (935,001–938,343) skip script verification. About **36,157 blocks (938,344–974,500, ~91.5%) get full script/signature checks**, so this sync is essentially a signature-verification-bound workload. Setting `-assumevalid` to a recent block is the single biggest CPU lever. The trust is the same kind as the default (a hash shipped with software), but Allod, not Core, would be the party vouching for it.

### Cited Findings
- v31.1 `src/kernel/chainparams.cpp` (mainnet): `consensus.defaultAssumeValid = uint256{"00000000000000000000ccebd6d74d9194d8dcdc1d177c478e094bfad51ba5ac"}; // 938343`. The running node logs the same hash — [chainparams.cpp v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/kernel/chainparams.cpp)
- Current master (future v32) has bumped it to `00000000000000000000748969ec33043c0e52a763c6dd5193861f559f2c72e3 // 966143` — [chainparams.cpp master](https://github.com/bitcoin/bitcoin/blob/master/src/kernel/chainparams.cpp)
- v31.1 `ConnectBlock` (validation.cpp) skips script checks for a block only if **all** of these hold: (1) the assumevalid hash is in the header index; (2) the block is an ancestor of the assumevalid block (otherwise the reason is "block height above assumevalid height" or "block not in assumevalid chain"); (3) the block is an ancestor of `m_best_header`; (4) best-header chainwork ≥ `MinimumChainWork()`; (5) the block is more than two weeks of proof-equivalent time below the best header ("block too recent relative to best header"). `-assumevalid=0` means "always verify" — [validation.cpp v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/validation.cpp)
- Source comment on the two-week rule: it "discourages hash power from extorting the network via DOS attack into accepting an invalid block through telling users they must manually set assumevalid. Requiring a software change or burying the invalid block, regardless of the setting, makes it hard to hide the implication of the demand." Comment on safety: skipping is safe "because block merkle hashes are still computed and checked" — [validation.cpp v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/validation.cpp)
- What is **still done** when scripts are skipped (same `ConnectBlock` code path): `Consensus::CheckTxInputs` (inputs exist in the UTXO view, amounts, fees, MoneyRange); BIP68 `SequenceLocks` (needs the UTXO lookup of each prevout height); `GetTransactionSigOpCost` accumulation against `MAX_BLOCK_SIGOPS_COST` (legacy, P2SH and witness sigop counting); UTXO spend/add and undo-data creation; plus `CheckBlock` (merkle root, PoW, sizes) and contextual header checks. Only `CheckInputScripts` (script interpreter plus ECDSA/Schnorr verification) is gated by `fScriptChecks` — [validation.cpp v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/validation.cpp)
- The CCheckQueue is only engaged when `fScriptChecks` is true (`if (queue.HasThreads() && fScriptChecks) control.emplace(queue)`). Below assumevalid, block connection is effectively single-threaded (UTXO/DB-bound) — [validation.cpp v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/validation.cpp)
- The "Enabling/Disabling script verification at block #N" log line is only printed when `role.validated && !role.historical`. A snapshot chainstate is not "validated" until background validation finishes, so these lines will **not** appear for the 935k→tip sync even though the switch happens at 938,344 — [validation.cpp v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/validation.cpp)
- Trust rationale from Core devs: assumevalid is set back from the tip only "because the chain might reorg", and minimum chain work should be "as far forward as possible" (gmaxwell, 2017) — [PR #10778 / #9779 discussion](https://mirror.b10c.me/bitcoin-bitcoin/9779/)
- Secondary source: the default hash is chosen in the open during the release process, reviewed on GitHub, and buried under months of PoW — [spark.money (secondary)](https://www.spark.money/research/bitcoin-core-assumevalid-fast-sync)

### Inferences
- Counts: 938,343 − 935,000 = 3,343 blocks skip scripts. 974,500 − 938,343 = 36,157 blocks get full checks (~91.5% of the 39.5k). With headers at 974,509 (from `getchainstates`), the two-week window (~2,016 blocks of equivalent work) covers about 972,500+. Those blocks would be fully checked even with a manual recent assumevalid.
- Manual `-assumevalid=<hash of ~block 972,000>` would remove script checks for ~37k blocks, leaving ~2.5k fully checked. All other rules (UTXO existence, amounts, sigop limits, PoW, merkle) still apply. The node still only accepts that block if it is in the most-work header chain and that chain meets minimum chain work. assumevalid never selects a chain.
- How Allod could use it safely: ship a hash per Allod release, pinned in the image and visible in the compose/env, cross-checked against multiple independent sources (e.g. ≥2 explorers plus a maintainer node), at least ~2–4 weeks deep at release time. Use it only for the initial sync, then drop it after sync (it has no effect once synced). The incremental trust is "Allod maintainers attest these scripts were valid". That is the same model as Core's default, but with Allod as signer and with less public review. If the hash is wrong or off-chain, Core simply falls back to full verification ("assumevalid hash not in headers" / "not in assumevalid chain"), so a stale or bad hash costs speed, not safety. This follows from the code paths above.
- The background chainstate (genesis→935,000) is entirely below 938,343, so it does no script verification at all with the default. Its cost is UTXO/disk/CPU for non-script checks only.

### Gaps
- No public per-block measurement found for "fraction of post-938k validation time that is script verification" on recent blocks. It is likely >50% with 16 threads, but that is unverified.

## 2. assumeutxo snapshot heights (v31 and planned v32)

### Takeaway
v31.1 mainnet ships snapshots at **840,000, 880,000, 910,000 and 935,000**. 935,000 is the newest usable in v31.1. Master has added **965,000**, which will very likely ship in v32. A snapshot is only loadable if its height and hash are in the running binary's chainparams, so a 965k snapshot needs v32+ (or a patched build).

### Cited Findings
- v31.1 mainnet `m_assumeutxo_data`: 840,000 (`hash_serialized a2a5521b…`, blockhash `…320283a0…a83a5`), 880,000 (`dbd19098…`), 910,000 (`4daf8a17…`), 935,000 (`hash_serialized e4b90ef9eae834f56c4b64d2d50143cee10ad87994c614d7d04125e2a6025050`, `m_chain_tx_count 1305397408`, blockhash `0000000000000000000147034958af1652b2b91bba607beacc5e72a56f0fb5ee`) — [chainparams.cpp v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/kernel/chainparams.cpp)
- Master mainnet `m_assumeutxo_data` adds `.height = 965'000` (alongside 840k/880k/910k/935k) — [chainparams.cpp master](https://github.com/bitcoin/bitcoin/blob/master/src/kernel/chainparams.cpp)
- Core docs: "any downloaded snapshot will be checked against a hash that's been hardcoded in source code ... keep in mind that the snapshot hash needs to be listed in the chainparams to make it usable. If there is no snapshot hash for the height you have chosen already, you will need to change the code there and re-compile." — [doc/assumeutxo.md v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/doc/assumeutxo.md)
- Issue #32377 (crowdsourced snapshot verification) has an Oct 2026 report of independently recomputing the 965,000 UTXO hash with Core 31.0 and matching chainparams — [#32377](https://mirror.b10c.me/bitcoin-bitcoin/32377/) (search snippet only, not fetched in full)

### Inferences
- With v32's 965k snapshot, post-snapshot work would be ~9.5k blocks instead of ~39.5k (~4× fewer). Those blocks would all be below v32's assumevalid (966,143) except the last ~8k, so CPU-heavy work drops even more.
- Allod could ship a patched v31.1 with an extra assumeutxo entry. That is a trust change the user must accept (Allod vouches for the UTXO hash, though background validation still checks it eventually), and it is a maintenance burden.

### Gaps
- I did not find the exact PR number or merge date for the 965,000 entry, or confirmation of v32's release date and final params.

## 3. -par / MAX_SCRIPTCHECK_THREADS and check-queue changes (v29–v31, master)

### Takeaway
In v31.1, `-par` defaults to 0 (auto = `hardware_concurrency()` − 1 workers). Workers are clamped to **MAX_SCRIPTCHECK_THREADS = 15**, so at most 16 verifying threads including the message-handler thread. This node already runs the maximum (log: 15 additional threads). The 22-thread 155H therefore uses 16. E/LPE cores are useful only because the scheduler can place script workers there. Raising `-par` cannot exceed 16. The parallel prevout-fetch PR (#35295) is merged on master (~July 2026), **not in v31.1**.

### Cited Findings
- v31.1 `validation.h`: `static constexpr int MAX_SCRIPTCHECK_THREADS{15};`. `chainstatemanager_args.h`: `DEFAULT_SCRIPTCHECK_THREADS{0}`. `chainstatemanager_args.cpp`: `-par<=0` → `script_threads += GetNumCores()`, then `worker_threads_num = script_threads - 1` ("the main thread counts towards the par threads"). `validation.cpp`: `m_script_check_queue{/*batch_size=*/128, std::clamp(options.worker_threads_num, 0, MAX_SCRIPTCHECK_THREADS)}` — [validation.h](https://github.com/bitcoin/bitcoin/blob/v31.1/src/validation.h), [chainstatemanager_args.cpp](https://github.com/bitcoin/bitcoin/blob/v31.1/src/node/chainstatemanager_args.cpp)
- `GetNumCores()` returns `std::thread::hardware_concurrency()` (logical CPUs, so 22 here) — [common/system.cpp v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/common/system.cpp)
- v31.1 `checkqueue.h` is still the classic mutex/condvar design: a shared `std::vector<T> queue`, `nIdle`/`nTodo` counters, batch size `max(1, min(nBatchSize, queue.size()/(nTotal+nIdle+1)))`, and the master thread joins verification at the end of the block — [checkqueue.h v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/checkqueue.h)
- v31.1 already contains `CoinsViewOverlay` (`m_connect_block_view`, layered on the coins cache for ConnectBlock), which is groundwork for parallel fetching. It has no `-prevoutfetchthreads` option — [validation.h v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/validation.h) (verified by grepping v31.1 init.cpp: no match)
- Master `init.cpp` has `-prevoutfetchthreads=<n>` ("prefetch block input prevouts from the chainstate database (0 disables, up to MAX, default ...)") — [init.cpp master](https://github.com/bitcoin/bitcoin/blob/master/src/init.cpp)
- PR #35295 (andrewtoth, successor of #31132): worker threads read block prevouts from the LevelDB chainstate to warm the cache before ConnectBlock. Default 8 threads, cap 16, 0 = serial. The description claims "1.18× to over 3× faster" IBD. l0rinc's reindex-chainstate benchmark (i7-7700, HDD, blocks 0–950,059): dbcache=1000 30,963 s → 26,651 s (1.16×); dbcache=50000 24,869 s → 25,187 s (1.01×, no gain when the UTXO set fits in cache) — [#35295 mirror](https://mirror.b10c.me/bitcoin-bitcoin/35295/), [#31132](https://mirror.b10c.me/bitcoin-bitcoin/31132)
- #35295 was described as "just merged" at the 9 Jul 2026 IRC meeting (newsletter dated 10 Jul 2026) — [This Week in Bitcoin Core #50](https://insider.btcpp.dev/p/fetching-block-input-prevouts-in)
- IBD tracking PR #32043 (l0rinc): reindex-chainstate on i9-9900K to height ~914k with dbcache 4500 and assumevalid: v28.2 27,039 s, v29.1 18,921 s, v30.0rc1 16,462 s. Full IBD v29.1rc1 vs master (Aug 2025, i9 SSD, to 909,090, 5 GB): 9h06m → 7h22m (21%). Merged speedups included #31551, #31144, #31645, #31868, #31682, #30442, #32279 (inline script storage). Tracking moved to #34280 in Jan 2026 — [#32043](https://mirror.b10c.me/bitcoin-bitcoin/32043/)

### Inferences
- `-par` gains nothing here because the node is already at the 16-thread cap. `-par=-N` or a lower value only helps if you want to leave cores for other containers (ldk-server, allod).
- On hybrid 155H: 6 P-cores × 2 SMT = 12 P-threads, plus 8 E-cores and 2 LPE-cores = 22 logical. With 16 verifier threads, about 4 will land on E/LPE cores (unless the OS packs differently). E-cores (Crestmont) are roughly 60–70% of P-core throughput on scalar integer work. LPE cores are much slower and run at low clocks. Because CCheckQueue uses dynamic, shrinking batches, slow cores cause little tail-latency penalty, so letting it use all cores is fine. Pinning to P+E cores (excluding the 2 LPE cores, e.g. `cpuset`) might help marginally. This is unmeasured inference.
- Prevout prefetch matters mainly when the UTXO set is not in cache. Here dbcache is 2 GB (capped by the 6 GiB container), so on v32 prefetch would likely help (the 1.16× case). It is not available in v31.1.

### Gaps
- No benchmark found for script-check scaling on Intel hybrid (P/E) CPUs specifically.

## 4. libsecp256k1 and SHA256 in v31.1; SHA-NI on the 155H

### Takeaway
v31.1 bundles libsecp256k1 **0.7.1** (Jan 2026). It has no batch verification: Schnorr batch verification is still an unmerged experimental PR, and ECDSA can't be batched. The 155H has SHA-NI, and bitcoind confirms it uses `x86_shani(1way;2way)`, the fastest SHA256 path. Hashing is therefore not a tunable bottleneck.

### Cited Findings
- v31.1 `src/secp256k1/CHANGELOG.md`: latest release entry `[0.7.1] - 2026-01-26`. Its fixes include an x86_64 asm feature-check bug that "could cause the build to fall back to the slower C implementation", plus extra stack clearing. 0.7.0 (2025-07-21) changes were build/API cleanups. No performance or batch-verify features are listed — [CHANGELOG v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/secp256k1/CHANGELOG.md)
- Schnorr batch verification lives in an experimental module (siv2r fork / upstream PR #1134), which is not merged. Secondary sources quote ~1.2× to "up to 2.5×" speedups (conflicting) — [siv2r/secp256k1#2](https://github.com/siv2r/secp256k1/pull/2), [spark.money glossary (secondary)](https://www.spark.money/glossary/batch-verification)
- v31.1 `src/crypto/sha256.cpp` implementations: `sha256_sse4`, `sha256d64_sse41`, `sha256d64_avx2`, `sha256d64_x86_shani`, `sha256_x86_shani`, selected via CPUID at startup — [sha256.cpp v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/crypto/sha256.cpp)
- Local: `/proc/cpuinfo` shows `sha_ni`, `avx2`, `sse4_1`, no `avx512f`. The node log says `Using the 'x86_shani(1way;2way)' SHA256 implementation` (local observation).
- Signature cache and script cache are 16 MiB each (log). During IBD, `ConnectBlock` passes `fCacheResults = fJustCheck` (false), so it consults but doesn't populate caches. With `blocksonly=1` there is no mempool pre-validation, so the caches give ~0 hits — [validation.cpp v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/validation.cpp)

### Inferences
- Signature verification (ECDSA for legacy/segwit v0, Schnorr for taproot) dominates CPU above assumevalid. With no batching and SHA-NI already active, CPU-side levers are limited to fewer verifications (assumevalid, newer snapshot) or more cores (already capped at 16).
- The libsecp 0.7.1 asm-detection fix only matters for custom builds. A release build (as logged) uses the asm path.

### Gaps
- No authoritative µs-per-verify numbers found for ECDSA/Schnorr on libsecp 0.7.x on this CPU class. `bench_verify`/`bench_schnorrsig` from the libsecp tree would give local numbers.

## 5. Cost of -blockfilterindex during IBD (and other indexes)

### Takeaway
The block filter index is built by its own background thread, so it costs little CPU during validation. With assumeutxo plus pruning, though, it has a nasty interaction. Indexes build only from genesis and in order, so they cannot index post-snapshot blocks until background validation reaches 935,000. **Un-indexed blocks are not pruned.** This node already runs with `blockfilterindex=0` during the initial sync. Enabling it later on a pruned node only works for blocks still on disk. A full filter index on a pruned node requires the blocks to be present at index-build time.

### Cited Findings
- doc/assumeutxo.md (v31.1): "Indexes work but don't take advantage of this feature. They always start building from the genesis block and can only apply blocks in order. Once the background validation reaches the snapshot block, indexes will continue to build all the way to the tip. For indexes that support pruning ... Blocks that are not indexed yet will also not be pruned ... these blocks can't be pruned until they are indexed, so they could consume a lot of disk space" — [doc/assumeutxo.md v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/doc/assumeutxo.md)
- In v31.1 init, `prune` is incompatible with `-txindex`, `-txospenderindex` and `-reindex-chainstate`, but **not** with `-blockfilterindex` — [init.cpp v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/init.cpp)
- Indexes start via `StartIndexBackgroundSync` / `BaseIndex::StartBackgroundSync()`, and base.cpp indexes from `ValidatedChainstate()` — [init.cpp v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/init.cpp), [index/base.cpp v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/index/base.cpp)
- A Core dev (2020): the blockfilterindex "is constructed locally in a background thread, so there shouldn't be any ibd slowdown" (design expectation, not a measurement) — [#18222](https://mirror.b10c.me/bitcoin-bitcoin/18222/)
- PR #26966 (parallelize index initial sync with worker threads) exists. Its merge status was not confirmed — [#26966](https://mirror.b10c.me/bitcoin-bitcoin/26966/)
- v31.0 added a new optional `-txospenderindex` (#24539) and raised default dbcache to 1024 MiB when ≥4096 MiB RAM is detected (#34692). The notes warn that in containers "the detected RAM may exceed the memory actually available" — [v31.0 release notes](https://bitcoincore.org/en/releases/31.0/)

### Inferences
- With `prune=10000` (~10 GB), assumeutxo and `blockfilterindex=1`, the 39.5k post-snapshot blocks (~60+ GB) could not be pruned until background IBD finishes. That would blow past the prune target. Keeping `blockfilterindex=0` during the fast sync (as the current profile does) is correct for disk reasons as much as for CPU.
- Building it later on a pruned node covers only blocks still on disk (~last ~10 GB ≈ several thousand blocks). Building from genesis would require `-reindex` (a full re-download), so in practice "enable later" means filters only from the enable height onward, with the index's own best block starting from where blocks exist. Whether Core accepts starting a blockfilterindex on a pruned node whose genesis-era blocks are gone needs verification (likely an init error, "previous blocks pruned").
- Building filters for retained blocks needs undo data per block (GCS construction with SipHash). This is cheap relative to signature checks; a typical estimate is minutes to under an hour for ~10k blocks, but this is unmeasured.

### Gaps
- No measured hours for building blockfilterindex from scratch on modern hardware were found.
- Exact v31.1 behaviour when enabling blockfilterindex on an already-pruned node was not verified in source (check `BaseIndex::Init` / the "best block of the index goes beyond pruned data" error path).

## 6. Background chainstate (genesis→935,000): competition, pausing, prioritisation

### Takeaway
Core prioritises the snapshot (tip) chainstate. Blocks for it are requested first, historical blocks only fill the remaining per-peer in-flight budget, and the tip chainstate gets 95% of the coins cache while in IBD. Both chainstates are connected **sequentially on the same thread** in `ProcessNewBlock`, so background work does add latency. v31.1 has **no RPC or option to pause or defer background validation**. The background chainstate is all below assumevalid, so it does no script checks and does not compete for the script-check thread pool. It competes for the validation thread, disk I/O and download bandwidth.

### Cited Findings
- `ProcessNewBlock` calls `ActiveChainstate().ActivateBestChain(...)`, then `HistoricalChainstate()->ActivateBestChain(...)` for the background chain in the same call (single validation thread, under cs_main per step) — [validation.cpp v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/validation.cpp)
- net_processing: "If there are multiple chainstates, download blocks for the current chainstate first, to prioritize getting to network tip before downloading historical blocks." `FindNextBlocksToDownload` runs first. `TryDownloadingHistoricalBlocks` gets only the leftover `MAX_BLOCKS_IN_TRANSIT_PER_PEER` (16) budget and skips limited peers. `BLOCK_DOWNLOAD_WINDOW = 1024` — [net_processing.cpp v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/net_processing.cpp)
- `MaybeRebalanceCaches`: while both chainstates exist and the node is in IBD, the historical chainstate gets 5% and the current/snapshot chainstate 95% of the coins tip and DB cache. After IBD (tip reached) the split flips: 95% to historical. When background validation completes, all goes to the snapshot chainstate — [validation.cpp v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/validation.cpp)
- The node runs `NODE_NETWORK_LIMITED` "until snapshot background sync completes" — [init.cpp v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/init.cpp)
- The only assumeutxo RPCs in v31.1 `rpc/blockchain.cpp` are `loadtxoutset` and `getchainstates` (plus `dumptxoutset`). No pause/defer RPC was found — [rpc/blockchain.cpp v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/rpc/blockchain.cpp)
- Usage doc: "As the background sync continues there will be temporarily two chainstate directories" — [doc/assumeutxo.md](https://github.com/bitcoin/bitcoin/blob/v31.1/doc/assumeutxo.md)

### Inferences
- On this node the background chainstate is already at 269,636 (normal IBD ran before `loadtxoutset`), so its remaining work covers 269,637→935,000, all with scripts skipped. Because downloads favour the tip chain, background block connects mostly happen when the tip chain is waiting on downloads. Its 5% cache (~100 MB of 2 GB) makes its connects slow and flush-heavy, but they interleave on the same thread.
- The only ways to "defer" background work in v31.1 are indirect: limit peers/bandwidth (risky) or accept it. A tool-side workaround (stop/restart) is out of scope and was not tested. No RPC exists.
- Once the tip chainstate exits IBD (reaches ~tip), the cache flips to the background chain, which then runs at full speed. So the post-snapshot tip sync is effectively prioritised already.

### Gaps
- No measurement of how much the interleaved background connects slow the tip chainstate's blocks/s.

## 7. Measured validation rates for recent mainnet blocks

### Takeaway
No public benchmark isolates "blocks/s above assumevalid on recent blocks". Published numbers are whole-chain IBD/reindex times, mostly with assumevalid on. Local measurement was not possible yet because the node was still activating the snapshot at research time.

### Cited Findings
- Whole-chain reindex-chainstate (i9-9900K, dbcache 4500, assumevalid default, to ~914k): v30.0rc1 16,462 s (~4.6 h), i.e. ~55 blocks/s averaged over all history (mostly assumevalid-skipped) — [#32043](https://mirror.b10c.me/bitcoin-bitcoin/32043/)
- Full IBD v30.0rc1 (i9, dbcache 20000, to 914,452): 23,018 s, bandwidth-limited — [#32043](https://mirror.b10c.me/bitcoin-bitcoin/32043/)
- Local (this node): blocks ~260,000–269,500 (2013, assumevalid-skipped, small) connected at ~200 blocks/s (500 blocks per ~2–3 s per `UpdateTip` timestamps) on dbcache 2 GB. These blocks are not representative of 2026 blocks (local observation).
- SwiftSync PoC benchmarks were posted on Delving (Falbesoner), but not fetched here — [Delving SwiftSync PoC](https://delvingbitcoin.org/t/swiftsync-speeding-up-ibd-with-pre-generated-hints-poc/1562/12)

### Inferences
- Rough expectation, unverified: a recent block has ~3–5k txs and ~5–10k inputs needing signature checks. At tens of µs per verify across 16 threads, that is ~20–50 ms CPU per block, plus UTXO/DB work. That suggests ~10–30 blocks/s CPU-bound for the ~36k script-checked blocks, i.e. roughly 20–60 min, if download keeps up. Download of ~60 GB is likely the bigger term. To measure, enable `-debug=bench` (needs a restart, not done) or compute from `UpdateTip` timestamps once the snapshot chainstate is syncing.

### Gaps
- No sourced blocks/s or MB/s for 2025–2026 blocks with full script checks on comparable hardware.

## 8. Upcoming techniques (SwiftSync, utreexo, prefetch) — status Nov 2026

### Takeaway
None are usable in v31.1. Parallel prevout prefetch (#35295) is merged on master for v32. SwiftSync has a Core PR (#34004, open) and a draft BIP (bips#2152, draft, "needs author update" May 2026). utreexo remains out-of-tree (utreexod / Floresta), not in Core.

### Cited Findings
- SwiftSync: near-stateless, parallelizable validation using a hints file (<100 MB) marking which outputs remain unspent. It can't reorg below the SwiftSync point (like pruning). A bad hints file can only waste time, not corrupt state — [Somsen gist](https://gist.github.com/RubenSomsen/a61a37d14182ccd78760e477c78133cd), [Optech 2025-04-11](https://bitcoinops.org/en/newsletters/2025/04/11/)
- Core PR #34004 "Implementation of SwiftSync" (rustaceanrob, Dec 2025, +723/−11, 15 files) proposes restricting SwiftSync to assumevalid with the hints file committed to the assumevalid block. Still under review (mutation-testing feedback from brunoerg); merge not confirmed — [#34004](https://mirror.b10c.me/bitcoin-bitcoin/34004/)
- Draft BIP bitcoin/bips#2152 for SwiftSync is in Draft, labelled needing author updates (May 2026) — [bips#2152](https://github.com/bitcoin/bips/pull/2152)
- #35295 prevout prefetch merged ~July 2026 on master (see §3) — [TWiBC #50](https://insider.btcpp.dev/p/fetching-block-input-prevouts-in)

### Inferences
- For Allod on v31.1 today, the actionable CPU levers are a newer assumevalid (big effect, trust trade-off) and a newer snapshot via v32 (fewer blocks). `-par` is already maxed, SHA-NI is already active, and indexes are already off. v32 would bring 965k snapshot + 966,143 assumevalid + prefetch, which would make the post-snapshot phase ~9.5k blocks, almost all with scripts skipped.
