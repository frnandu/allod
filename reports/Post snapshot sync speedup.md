# Fix the charger, then unclamp memory

On this laptop the biggest obstacle between the 935,000 snapshot and the tip is the power supply, not Bitcoin Core. The USB-C source negotiated **5 V × 3 A (15 W)** instead of 20 V. The CPU then ran at **0.4–1.3 GHz** (a pinned busy loop measured 600 MHz against a 4.8 GHz maximum) at only 63–66 °C, and the measured tip sync ran at **2.07 blocks/s**. That projects to about **5.3 h from bitcoind start to tip** (ETA ~14:00 UTC for a 08:43 start) ([Live node](file:///home/fmar/workspace/allod/research_notes/Post%20snapshot%20sync%20speedup/local_measurements_config.md)). The second obstacle is Allod's own memory policy. The container sat exactly at its **6 GiB** cgroup limit, page cache was squeezed to ~2.7 GB against an 11 GB snapshot chainstate, and the code caps sync `dbcache` at 2 GiB, while SPEC §2.3.2 still says up to 16 GiB ([sync-tuning.sh](file:///home/fmar/workspace/allod/images/bitcoind/sync-tuning.sh), [SPEC.md](file:///home/fmar/workspace/allod/SPEC.md)). Neither is a network problem: the ~30 MB/s link averaged 3.6 MB/s, and downloading the whole 65–70 GB range at link speed would take only ~37–40 min. Fixing the charger, raising the memory limit together with dbcache, temporarily raising the prune target and starting fast sync as soon as headers arrive plausibly brings time-to-tip to **~1.3–1.8 h**. An opt-in recent `assumevalid` approaches the ~1 h network floor, and Core v32's 965,000 snapshot would cut the post-snapshot range by ~4×. All "after" figures are estimates. None was measured on this host, because the stack was removed by an external actor at 10:00:45 UTC.

## The live run was never network-bound; it was clock- and cache-bound

The node started at 08:43:34 and had headers to 974,508 two minutes later. It then spent ~18 min on from-genesis IBD before fast sync was requested at 09:03:50. The 8.8 GB snapshot downloaded in ~5 min at ~30 MB/s. `loadtxoutset` took **13 min 34 s**: a 10.7 min coin load that included 11 intermediate wiping flushes (~252 s), a 12.7 s final save, and a **2 min 35 s** UTXO-hash check on a single `b-http_worker` thread at 99%. Networking resumed at 09:21:59 ([Live node](file:///home/fmar/workspace/allod/research_notes/Post%20snapshot%20sync%20speedup/local_measurements_config.md)). The two notes count the flushes as 11 and 12. The twelfth duration is the final save, so both are right. Tip sync then went through three phases:

| Phase (UTC) | Heights | blocks/s | Net RX MB/s | Container CPU | Bottleneck |
|---|---|---|---|---|---|
| A, cold cache, 09:22–09:25 | 935,002→935,167 | **0.74** | 7.2 | 89% | serial msghand thread + LevelDB reads with an empty coins cache |
| B, below assumevalid, 09:26–09:49 | 935,176→938,256 | **1.78–2.75** | 1.7–4.2 | 82–98% | single `b-msghand` thread on a clamped clock; 15 script threads idle |
| C, script checks, 09:50–10:00 | 938,308→939,725 | **2.35–2.46** | 4.1–4.2 | **516–614%** | script verification on 16 threads at ~0.4–1.3 GHz |
| Whole run, 09:22–10:00 | 935,002→939,725 | **2.07** | 3.6 | 242% | — |

The network evidence shows the node starving itself. All **159 block slots** stayed full (16 per peer across 10 peers), received bytes stayed flat for 30 s at a time, and peer pings rose to **30–174 s** because the message handler could not service sockets. The cgroup recorded **42,626 `sock_throttled`** events, 33 M page-cache refaults and NVMe reads of 140–425 MB/s at low utilisation (io.pressure full ~4.8%). In other words, disk *latency* stalls a single thread, and disk bandwidth is not the limit ([Live node](file:///home/fmar/workspace/allod/research_notes/Post%20snapshot%20sync%20speedup/local_measurements_config.md)). This fits Core's own position that long syncs are validation-bound, not download-bound ([bitcoin/bitcoin#34121](https://mirror.b10c.me/bitcoin-bitcoin/34121/)).

The phase data contains a telling detail. Phase B skipped script checks and phase C did not, yet phase C was *no slower* (2.4 vs ~2.2 blocks/s). On a clamped CPU, the serial path dominates both phases: one thread does UTXO lookups, `CheckTxInputs`, sigop counting and undo writes. Below assumevalid, block connection runs on one thread, because the check queue is used only when `fScriptChecks` is true ([validation.cpp v31.1](https://github.com/bitcoin/bitcoin/blob/v31.1/src/validation.cpp)). The 15 script workers absorb the signature work in parallel. So the levers that speed up the serial thread (clock speed, cache hits) come before the levers that remove signature work (assumevalid).

The power diagnosis rests on several observations. The source reported `voltage_now=5000000`, `current_now=3000000`, `usb_type PD_PPS` and `voltage_max` 20 V. BAT0 read "Not charging". Package-throttle counters rose by ~63k in 12 minutes at a cool 63–66 °C, and the OS power settings were already maximal (EPP `performance`, `no_turbo 0`, RAPL PL1 = PL2 = 64 W). That points to the embedded controller limiting the CPU on the 15 W input, not to heat or software ([Live node](file:///home/fmar/workspace/allod/research_notes/Post%20snapshot%20sync%20speedup/local_measurements_config.md)). The exact limit reason (PL1, PROCHOT or EDP) is unconfirmed, because `turbostat` and MSR reads need root. `sudo turbostat --show Busy%,Bzy_MHz,PkgWatt -i 5` would settle it.

## Conflicting notes resolved: live config beats defaults and SPEC

The notes disagree in several places. In each case the direct live reading wins. **Memory limit:** `deploy/compose.yaml` defaults `mem_limit` to `${BITCOIN_MEMORY_LIMIT:-2g}`, but `docker inspect` on the running container showed `Memory=6442450944` and cgroup `memory.max` was 6 GiB. This deployment overrode the default to 6 GiB, and fresh installs still get 2 GiB ([compose.yaml](file:///home/fmar/workspace/allod/deploy/compose.yaml), [Live node](file:///home/fmar/workspace/allod/research_notes/Post%20snapshot%20sync%20speedup/local_measurements_config.md)). **Block filter index:** the brief and the compose default say `blockfilterindex=1`, but the generated `/data/bitcoin.conf`, the env (`BITCOIN_BLOCKFILTERINDEX=0`) and the log line `Config file arg: blockfilterindex="0"` all show it was **off** during this run. The run therefore measures nothing about index cost. A default install, however, runs this sync with the index **on**. **dbcache:** SPEC §2.3.2 says 60% of memory above 2 GiB, up to 16 GiB, and records a live `dbcache=16384`. The code caps it at half of headroom and at most 2048 MiB. Commit `50541fe` ("cap bitcoind memory so it cannot exhaust the host") made that change on purpose without updating SPEC. The code is what runs, so the live `dbcache=2048` is correct for the code, and SPEC is stale ([sync-tuning.sh](file:///home/fmar/workspace/allod/images/bitcoind/sync-tuning.sh)). The minor disagreements (named volume vs bind mount, `none` vs `mq-deadline` scheduler) do not matter: both storage paths are a plain host ext4 directory with no overlayfs, and no evidence shows the scheduler matters on NVMe. Finally, SwiftSync's Core PR #34004 is reported in one note as "under review" and in another as **closed unmerged on 2026-05-31**. The dated closure is more specific and is the one used here ([PR #34004](https://mirror.b10c.me/bitcoin-bitcoin/34004/)).

## Ranked changes, from hardware to trust model

The ranking puts the largest expected gain on this machine first, and notes where general Allod deployments differ. Speedups marked "est." are inferences from the measured phases and published benchmarks. None was measured on this workload.

| # | Change | Expected effect | Evidence | Trade-off | Where |
|---|---|---|---|---|---|

| 2 | **Memory limit and sync dbcache scaled together** (e.g. 20 GiB limit, ~11 GiB dbcache here) | est. **15–35%**, more in cold-cache phases; general installs on the 2g default gain most | 450→2000 MiB: 1.18–2.46× on reindex ([#34641](https://github.com/bitcoin/bitcoin/pull/34641)); 450→16384 full IBD 1.47× ([#28280](https://github.com/bitcoin/bitcoin/pull/28280)) | OOM-kill risk under a hard, swapless limit, which forces a cold restart | `sync-tuning.sh`, `compose.yaml`, installer |
| 3 | **Temporarily raise the prune target** (e.g. 100,000–150,000 MiB during sync) | est. **5–15%** (bigger at large dbcache) | Prune halves per chainstate; ~500 prune Syncs at prune=10000; fewer prune flushes gave 15–21% ([#20827](https://mirror.b10c.me/bitcoin-bitcoin/20827/)) | 50–75 GB of temporary block disk | `sync-tuning.sh` / entrypoint |

**Memory is the lever Allod controls, and the default is the worst case.** Fresh installs run under a 2 GiB limit. `mem_mib()` subtracts 768 MiB *and* `memory.current`, which counts page cache, then halves the result. A typical 2g install therefore syncs with a dbcache of a few hundred MiB, below even v31's own 1024 MiB default ([v31.0 release notes](https://bitcoincore.org/en/releases/31.0/)). That is exactly the range where l0rinc's benchmarks show the steepest gains: 22,077 s → 18,302 s on an i9 and 33,619 s → 28,353 s on an Umbrel N150 going from 450 to 2000 MiB ([PR #34641](https://github.com/bitcoin/bitcoin/pull/34641)). Beyond dbcache, the live run shows the cgroup limit also caps the OS page cache that LevelDB's tiny 8 MiB cache depends on ([dbwrapper.cpp](https://github.com/bitcoin/bitcoin/blob/v31.1/src/dbwrapper.cpp)). Wipes cost a lot too. In v31.1 the coins cache is emptied only at ≥90% full or on forced flushes, and prune and hourly writes use a non-wiping `Sync()` ([validation.cpp](https://github.com/bitcoin/bitcoin/blob/v31.1/src/validation.cpp)). At the observed ~0.5–0.67 MiB/block of growth, a 1.9 GiB snapshot cache wipes **~13–15 times** over 39.5k blocks, and each wipe restarts a phase-A-like cold period. An ~11 GiB cache cuts that to ~2–4 wipes (extrapolated). The full UTXO set (~143 B/coin × 164 M ≈ 23.5 GB) does not fit on this host and does not need to. The cache starts empty after activation either way, so only the 39.5k-block working set matters. The trade-off is real: commit `50541fe` added the cap because an uncapped profile starved the rest of the stack. v31 itself warns that RAM detection overstates container memory, and l0rinc reports OOMs "on some flushes" at the edge ([PR #34641](https://github.com/bitcoin/bitcoin/pull/34641)). The fix is to size from the *limit* with a page-cache reserve, not to drop the safety margin. The live sample measured anon ≈ dbcache + ~1.4 GB.

**Pruning interacts badly with assumeutxo at Allod's sizes.** With two chainstates, the prune target per chainstate is halved (`PruneTarget / num_chainstates`), so `prune=10000` really means 5,000 MiB. The IBD buffer of 1 MB × remaining blocks (~39.5 GB) exceeds that until the very end, so the node prunes on roughly every new 128 MiB block file: **~500 prune Syncs**, each writing every dirty coin and wasting the FRESH-coin savings ([blockstorage.cpp](https://github.com/bitcoin/bitcoin/blob/v31.1/src/node/blockstorage.cpp)). `prune=100000` removes prune events for the first ~9k blocks and roughly halves them after that. `≳150000` removes nearly all of them. Lowering the value back afterwards is legal, while `prune=0` is not, because an already-pruned node needs a full `-reindex` to unprune ([chainstate.cpp](https://github.com/bitcoin/bitcoin/blob/v31.1/src/node/chainstate.cpp)). Blocks ≤935,000 are kept for background validation regardless.

**`assumevalid` is a trust lever, not a free one.** Core skips scripts only for ancestors of the assumevalid block that sit more than two weeks of work below the best header. All other consensus checks (inputs exist, amounts, sigops, merkle, PoW) still run, and a hash that is wrong or off-chain falls back to full verification, so it can cost speed but never safety ([validation.cpp](https://github.com/bitcoin/bitcoin/blob/v31.1/src/validation.cpp)). For Allod the incremental trust is "Allod maintainers attest these scripts were valid", with less public review than Core's release process. That justifies an explicit opt-in (`BITCOIN_SYNC_ASSUMEVALID`), never a silent default. Its value depends on the machine. On the clamped CPU, phase B ≈ phase C shows it would save little. Once the clock and cache are fixed, signature checking becomes the dominant per-block cost and the gain grows.

**What does not help.** `-par` is already at the 15-worker ceiling, and `-maxconnections` cannot add outbound download peers ([net.h](https://github.com/bitcoin/bitcoin/blob/v31.1/src/net.h)). SHA-NI is already in use, and libsecp256k1 0.7.1 has no batch verification ([CHANGELOG](https://github.com/bitcoin/bitcoin/blob/v31.1/src/secp256k1/CHANGELOG.md)). `-reindex-chainstate` is rejected in prune mode and would wipe the snapshot ([init.cpp](https://github.com/bitcoin/bitcoin/blob/v31.1/src/init.cpp)). LevelDB, filesystem and scheduler knobs have no evidence of mattering on NVMe. Larger dbcache during `loadtxoutset` saves ≤5–10%, because every coin is written exactly once ([PR #35195](https://mirror.b10c.me/bitcoin-bitcoin/35195/)). Shipping post-snapshot blocks on the USB image only saves download time, the cheap part, and `-loadblock` loses the download/validation overlap ([bitcoin/bitcoin#34121](https://mirror.b10c.me/bitcoin-bitcoin/34121/)). An `-addnode` to a fast archival peer helps only where random peers are slow (Tor, congested links). Here 159 slots were already full. Background validation cannot be paused in v31.1, but Core already gives the tip chain download priority and 95% of the cache during IBD ([net_processing.cpp](https://github.com/bitcoin/bitcoin/blob/v31.1/src/net_processing.cpp)).

## Concrete edits for Allod's four files

**`images/bitcoind/sync-tuning.sh`.** Replace the fixed 2048 MiB cap in `sync_dbcache` with a limit-relative cap: for example, dbcache ≤ min(16384, (cgroup limit − 3 GiB) × ~0.75, 60% of host memory above 2 GiB), never below `BITCOIN_DBCACHE`. That keeps ≥1.5 GiB for anon overhead plus a page-cache reserve. In `mem_mib`, base cgroup headroom on `memory.max` minus `anon` from `memory.stat` (or minus a fixed overhead), not `memory.current`, which counts reclaimable page cache. Keep `steady_dbcache` on the conservative cap so the post-sync profile stays small. Extend `sync_profile` to emit `blockfilterindex=0`, a raised `prune=` when free disk allows it (reuse `prune-size.sh`, and leave headroom for ~70 GB of post-snapshot blocks), and, only when `BITCOIN_SYNC_ASSUMEVALID` is set, `assumevalid=<hash>`. Every operator-set line in `BITCOIN_EXTRA_CONF` stays untouched, as today. The existing `watch_sync` restart at `initialblockdownload=false` already reverts all of these, which is what makes them safe as sync-only settings.

**`images/bitcoind/bitcoind-entrypoint.sh`.** Currently it unconditionally writes `prune=$PRUNE` and `blockfilterindex=${BITCOIN_BLOCKFILTERINDEX:-1}` ([entrypoint](file:///home/fmar/workspace/allod/images/bitcoind/bitcoind-entrypoint.sh)). It should skip those lines when the sync profile supplies them, the same way it already handles `dbcache`, so each key appears exactly once. It should also log the effective memory limit and dbcache, so field reports show what ran.

**`images/bitcoind/assumeutxo.sh`.** The script already pauses networking during the download and resumes after load, and that is correct. The 18-minute gain comes from the setup wizard writing `fastsync-request.json` as soon as the base header is known, or from the script acting on a pre-accepted default. Optionally, after `loadtxoutset`, warm the page cache by sequentially reading `chainstate_snapshot/*.ldb`. With a large enough memory limit this would shorten phase A. This is unmeasured, and it only helps if the cgroup has room for the 11 GB.

**`deploy/compose.yaml` and `.env.example`.** The hard `mem_limit: 2g` default caps all of the above. Have the installers (VPS, Umbrel, StartOS, ISO `allod-data-setup`) write a host-sized `BITCOIN_MEMORY_LIMIT`, for example min(dbcache_target + 4 GiB, ~65% of RAM), which is ~20g on this 30 GB host. Keep `memswap_limit` equal to it to forbid swap. Change the `BITCOIN_BLOCKFILTERINDEX` documentation to say it takes effect after the initial sync. Fix the `.env.example` comment ("max 2 GiB"). Per AGENTS.md, SPEC §2.3.2 must be updated in the same change. It currently describes neither the shipped 2 GiB cap nor any of these new rules.

## Time-to-tip before and after

| Scenario (this host, cumulative) | Pre-load (headers + download + load) | Tip sync (39.5k blocks) | Total from bitcoind start |
|---|---|---|---|
| **Measured baseline** (15 W, 6 GiB, dbcache 2048, prune 10000) | 18 min wasted + 5 + 13.5 min | **~4.6–4.7 h** (38 min measured at 2.07 blocks/s, then ~34.8k blocks at the measured 2.35–2.46) | **~5.3 h** (ETA ~14:00) |
| + fast sync right after headers | 2 + 5 + 13.5 min | ~4.7 h | ~5.0 h |
| + 65 W charger | ~2 + 5 + ~6 min (est.) | est. 1.6–2.2 h | est. **~1.8–2.4 h** |
| + 20 GiB limit, ~11 GiB dbcache, prune 100k–150k, filter index off | ~2 + 5 + ~5.5 min | est. 1–1.5 h | est. **~1.3–1.8 h** |
| + opt-in assumevalid ~4 weeks deep | same | est. 45–70 min (network floor ~37–40 min) | est. **~1–1.3 h** |
| v32 with 965,000 snapshot instead | same | est. 15–30 min for ~9.5k blocks | est. **~35–50 min** |

The baseline projection assumes the rate of 939k-era blocks holds to the tip. Blocks from 2026 could shift it by ±20%, and a restart after the 10:00 stack removal brings back the cold 0.74 blocks/s phase for several minutes. The charger estimate assumes effective clocks of ~3.5–4.5 GHz and that I/O latency does not scale with them, which is why it is below the raw 4× clock ratio. For general deployments the ordering shifts. Desktops and VPSes on stable power never hit the clamp, so the memory-limit fix moves to first place. On 8 GB mini-PCs and Pi 5-class devices the 2g default currently holds the sync below v31's own default dbcache.

## Conclusion

The run shows that "fast sync" on Allod is bounded by the host and by Allod's guardrails, not by Bitcoin Core or the network. The serial validation thread sets the pace whenever it is starved of clock or cache, which is why removing signature work barely mattered on the clamped CPU. The order of fixes follows from that: power, then memory and pruning, then trust-model shortcuts. The 2 GiB cap fixed a real starvation bug, but it now costs every default install hours. The better design sizes bitcoind from an installer-chosen memory limit, keeps a page-cache reserve, and makes every sync-only setting (dbcache, prune, filter index, optional assumevalid) revert automatically through the existing restart.

The remaining uncertainty is quantitative. Every "after" number here is an estimate, and the stack removal ended the measurement. One controlled rerun on a 20 V charger with a 20 GiB limit, sampled the same way, would replace the estimates with facts. Adding a PD-voltage check to the ISO status script would stop the next laptop user from losing four hours to a cable.
